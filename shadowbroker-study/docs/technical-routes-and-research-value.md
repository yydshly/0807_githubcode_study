# ShadowBroker 对你的价值与值得复用的技术路线

## 结论

ShadowBroker 对你的最大价值，不是提供一套“完整、可靠的全球实时监控数据”，也不是直接把整个项目复制成自己的产品。

它更适合作为一个多源公开信息系统的参考样本：研究数据源从哪里来、怎样接入、怎样统一成时空对象、怎样判断新鲜度和可靠性，以及怎样展示和回放。

建议把它定位成：

> 公开数据源目录 + 多协议接入实验室 + 时空数据处理参考架构。

其中数据源和接入方式是第一优先级，统一模型、质量控制和历史存储是第二优先级，地图展示和高级分析是第三优先级。

## 价值层次

```text
来源发现与许可
      ↓
REST / RSS / WebSocket / TCP / MQTT / 设备推送
      ↓
统一对象、事件、位置和时间模型
      ↓
缓存、去重、质量、健康度和来源回退
      ↓
地图、时间线、检索、告警和多源关联
```

如果只参考地图界面，会错过这个项目真正值得研究的部分。最有价值的是前四层。

三层路线的逐项目标、输入输出、核心机制、风险和验收标准，见 [P0–P2 技术路线整理与说明](p0-p2-technical-route-guide.md)。

## P0：最值得优先复用的技术路线

### 1. 数据源目录与来源治理

把每一个来源当成独立资产管理，而不是把网址散落在代码中。

每个来源至少记录：

- 领域、官网、接口文档和数据用途；
- 免费、注册、密钥、配额、商业使用和再分发条件；
- 协议、认证方式、请求参数和返回格式；
- 原始时间字段、更新频率、覆盖范围和已知缺口；
- 代码适配器、备用源、最后验证日期和当前状态。

这条路线可以直接形成你所有研究项目共享的 `source-registry`。它的价值高于单独保存某个抓取脚本。

### 2. 可插拔来源适配器

ShadowBroker 将不同来源拆成 fetcher、stream client 和设备入口，这是值得保留的结构。

建议形成统一接口：

```text
SourceAdapter
├─ fetch() / connect()
├─ normalize()
├─ validate()
├─ checkpoint()
├─ health()
└─ provenance()
```

以后增加卫星、地震、天气或新闻来源时，只增加适配器，不修改整个系统。

### 3. 多种接入协议的统一处理

这是该项目最有教学价值的部分之一。

| 接入路线 | 项目中的例子 | 值得研究的重点 |
|---|---|---|
| REST/JSON 轮询 | USGS、天气、遥感目录 | 分页、增量游标、配额、条件请求 |
| RSS/Atom | 新闻源 | ETag、发布时间、正文去重、失效源检测 |
| WebSocket | AISStream | 订阅、心跳、断线重连、指数退避、背压 |
| TCP 长连接 | APRS-IS、JS8Call | 行协议、粘包、重连、认证和限速 |
| MQTT | Meshtastic | Topic、QoS、保留消息、节点身份 |
| 设备 HTTP 推送 | AIS-catcher | 节点鉴权、批量上报、幂等和离线缓存 |
| 文件/目录数据 | 静态设施、名单 | 版本、校验和、更新日期和来源许可 |

应该把这些协议做成小型、可独立运行的实验，而不是依赖整个 ShadowBroker 才能验证。

### 4. 统一的时空数据模型

不同领域虽然字段不同，但可以抽象成两类核心数据：对象和事件。

```text
Entity：卫星、飞机、船舶、接收站、设施
Event：地震、天气预警、火灾、新闻事件、靠港、相遇
```

推荐公共字段：

```text
source_id / source_record_id
entity_id / event_id
lat / lng / geometry
observed_at / published_at / fetched_at
source_url / adapter_version
confidence / freshness / quality_flags
raw_payload_ref
```

特别重要的是区分三个时间：现场观测时间、上游发布时间和本项目抓取时间。地图刷新时间不能冒充数据发生时间。

### 5. 可靠性、缓存与来源回退

公开免费源经常限流、失效、改版或返回空数据，因此下面这些能力比“多接几个源”更重要：

- 本地最后成功快照；
- ETag、Last-Modified 和条件请求；
- 超时、重试、指数退避和熔断；
- 主源、备用源和降级模式；
- 记录最后成功时间、条目数变化和错误原因；
- 区分“功能未配置”“来源不可用”“成功但零条数据”；
- 防止旧缓存伪装成实时数据。

这条路线可以独立形成一个 `source-health-monitor` 项目，为以后所有采集项目复用。

## P1：第二阶段值得深入的技术路线

### 6. 目录数据加本地计算

卫星路线非常典型：下载公开 OMM/轨道参数，再用 SGP4 在本地推算当前位置。

这类架构适用于“上游提供低频参数，本地生成高频状态”的问题。必须明确区分：

- 上游参数更新时间；
- 本地计算时间；
- 推算误差和参数老化；
- 公开目录完整度。

适合建立独立的 `satellite-full-catalog` 项目，研究全量公开目录、OMM、SGP4、轨道新鲜度和大规模可视化，而不是沿用当前精选的约 490 颗专题目录。

### 7. 地理空间增强

经纬度只有与边界和区域结合后才产生业务含义。

值得复用的处理包括：

- 点落在哪个国家、行政区、领海、EEZ 或公海；
- 目标与港口、机场、基地、灾害区的距离；
- 轨迹与禁区、预警区、航线的相交；
- 网格化聚合、热区和区域统计；
- 对争议边界保留多个声索结果和数据来源。

建议单独建立 `geospatial-enrichment`，避免把空间判断写死在每个数据源适配器中。

### 8. 新闻、RSS 与 GDELT 事件管线

这一方向的价值不在于把每篇新闻放上地图，而在于研究：

```text
采集 → 正文规范化 → 去重 → 实体提取 → 地名解析
     → 事件分类 → 来源聚合 → 置信度 → 时间线
```

GDELT 是新闻驱动的结构化线索，不是权威现场事件数据库。应保留原始报道、媒体数量、去重组和交叉来源，不能把 GDELT 条目直接当成已确认事实。

### 9. 历史快照与 Time Machine

实时地图只能回答“现在收到什么”，历史存储才能研究变化和来源质量。

建议存储：

- 原始响应或其内容哈希；
- 规范化对象和事件；
- 每个来源的抓取运行记录；
- 位置轨迹和状态变化；
- 数据修订、删除和来源回补。

数据量大时，不要每分钟保存整个世界的完整 JSON。应使用增量事件、轨迹点抽样、分区存储和保留策略。

### 10. 大规模地图展示

地图的研究价值在于验证时空模型，不应成为第一阶段重点。

值得参考的技术包括：

- GeoJSON Source 与图层分离；
- 视口裁剪、聚类、网格和热力图；
- 全球缩放时展示聚合，局部放大时展示单体；
- 高频移动目标插值；
- Web Worker 或服务端批处理；
- 不同缩放级别的细节层次控制。

例如全量公开卫星不能简单绘制一万多个重叠图标；需要聚合、筛选和按视野传播位置。

## P2：有条件再研究的路线

### 11. 多源关联与告警

只有完成来源、统一模型和质量标记后，才适合研究：

- 地震与海啸/天气预警关联；
- AIS 船位与港口、领海、EEZ、SAR 检测关联；
- 飞行轨迹与机场、空域关联；
- 新闻/GDELT 与直接观测事件关联；
- 同一对象跨来源身份解析。

告警必须附带证据来源、时间差和置信度，避免用简单距离规则制造大量误报。

### 12. 边缘设备和多点接收

本地 AIS、ADS-B、无线电和 Meshtastic 展示了设备进入中心系统的路线：

```text
天线/传感器 → 边缘解码 → 本地缓存 → 安全上传
            → 中心去重 → 来源与节点质量评估
```

只有当你需要拥有某个地区的一手覆盖时才需要多点部署。研究第三方公开聚合源时，一台中心机器即可。

## 不建议当前投入的部分

以下能力可以归档观察，但不应进入第一阶段主线：

- InfoNet、Wormhole、自动组网和实验隐私网络；
- 摄像头大目录和不稳定的网页抓取；
- 预测市场、金融和与核心研究无关的安全扫描；
- AI 问答外壳和缺少证据链的自动情报结论；
- 为了视觉效果堆叠大量低质量图层。

这些模块增加依赖、凭据和安全面，但不直接提升公开来源接入研究能力。

## 对你最合适的项目拆分

不建议继续在 ShadowBroker 源码里无限增加功能。更合适的是把它拆成多个可独立验证的小项目：

```text
00-source-registry/              数据源、许可、协议与验证日期
01-protocol-labs/               REST、RSS、WebSocket、TCP、MQTT、设备推送
02-satellite-full-catalog/      OMM、SGP4、全量公开卫星和轨道新鲜度
03-disaster-feeds/              地震、天气、火灾和官方预警
04-news-gdelt-events/           新闻去重、实体、地理编码和事件聚合
05-maritime-ais/                AIS流、船旗国、领海/EEZ和覆盖缺口
06-geospatial-enrichment/       通用空间匹配与区域统计
07-source-health-monitor/       缓存、配额、错误、SLO和来源回退
08-spatiotemporal-store/        轨迹、事件历史、快照和回放
09-unified-map/                 最后再做统一地图展示
```

每个项目都应先输出：来源说明、最小接入程序、原始样例、规范化模型、数据质量报告和可重复测试。完成这些以后再接入统一地图。

## 推荐执行顺序

### 第一阶段：来源与协议

1. 建立来源注册表。
2. 分别跑通 REST、RSS、WebSocket、TCP、MQTT 和本地 HTTP 推送。
3. 为每类协议保存最小原始样例。

### 第二阶段：统一数据与可靠性

1. 定义对象、事件、位置和三个时间字段。
2. 建立缓存、重试、限流和来源健康记录。
3. 保留原始数据引用和来源证据。

### 第三阶段：四个核心领域

1. 卫星全量公开目录。
2. 地震、天气和火灾。
3. 新闻、RSS 和 GDELT。
4. AIS 船舶作为实时流和设备接入实验。

### 第四阶段：时空分析与展示

1. 空间边界匹配。
2. 历史轨迹和事件回放。
3. 多源关联和质量评分。
4. 聚合地图和专题视图。

## 是否需要部署

学习接入协议和验证来源时不需要公网部署，本地运行即可。

只有出现以下需求时才值得部署长期服务：

- 需要 24 小时连续接收 WebSocket、TCP 或 MQTT；
- 需要积累历史轨迹和来源可用率；
- 需要多个设备节点向中心上传数据；
- 需要多人远程访问同一套结果。

部署的目的应是连续采集和形成自己的历史数据库，而不是单纯把地图放到公网。

## 最终判断

ShadowBroker 值得研究，但应当“拆解学习”，不应当“整体照搬”。

最值得带走的是：

1. 来源注册与许可治理；
2. 多协议采集适配器；
3. 统一时空模型和证据字段；
4. 缓存、健康度、回退和数据新鲜度；
5. 目录加本地计算、空间增强和历史回放。

地图、AI 和复杂关联属于后续消费者。只有前面的来源与数据基础可靠，后面的展示才有实际意义。
