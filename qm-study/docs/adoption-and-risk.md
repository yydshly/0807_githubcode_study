# QM 采用建议与风险边界

## 适合的场景

QM 最适合一个组织内部的多人 Agent 场景：员工既需要个人助手，又要在项目频道中共享工作，并且记忆、文件和凭据不能混成一套。

典型场景：

- 研发频道中的代码、CI、日志与项目汇报 Agent；
- 跨邮件、文档、数据库和网页的组织知识助手；
- 个人邮件处理与共享项目跟踪并存；
- 团队创建、审查和推广 Skills；
- 在权限范围内生成和发布内部 Web 应用；
- 定时运行、无人值守、结果回投协作频道的后台任务。

## 不适合直接采用的场景

- 单人、本地、偶尔使用的聊天助手；
- 以确定性节点为主的传统 BPM；
- 面向公众、需要强租户边界的 Agent SaaS；
- 希望开箱即用满足监管认证的生产系统；
- 没有身份、数据库、云基础设施和安全运营能力的团队；
- 主要使用飞书、企业微信或钉钉，但没有 Surface Adapter 开发预算的团队。

## 与当前研究项目的关系

| 现有方向 | QM 的关系 |
|---|---|
| ShadowBroker / Horizon / Yichen Skills | 作为数据源、工具或外部服务接入 QM，而不是被 QM 替代 |
| AgentScope | 位于不同抽象层；需要自建 Harness Adapter 才能直接组合 |
| David Ondrej Skills | 可作为个人和通用能力候选，需要 QM 的权限与审查改造 |
| Matt Pocock Skills | 可作为研发 Agent 的工程纪律层，QM 提供持续环境和团队治理 |
| GitHub Pages 门户 | 只能展示研究结论，不能承载 QM 后端、数据库、沙箱或密钥 |

## 主要安全风险

以下风险来自上游公开安全说明，不能用“已经有 Scope”一笔带过：

1. **命令策略不是沙箱边界。** 文本规则可以被编码、混淆或先写脚本再执行等方式绕过。
2. **浏览器动作门禁不完整。** 部分浏览器操作不重新进入命令策略和逐命令审批。
3. **凭据使用时是明文。** 沙箱进程可以读取已物化的环境变量或文件。
4. **用途不是强授权。** Grant 的 purpose 有助于提示和审计，但不能限制已进入沙箱的凭据实际用途。
5. **Prompt Injection 筛查是启发式。** 命令输出、多模态、部分 webhook 和其他数据路径没有完整覆盖。
6. **混合权限过滤仍有缺口。** 并非所有上下文条目都有完整来源标签。
7. **出网控制依赖后端。** 不同 Sandbox Backend 的域名/IP 强制能力并不一致。
8. **管理员是特权内容读取者。** 管理员可审计地读取对话、记忆、文档和凭据元数据等敏感内容。
9. **数据保留较长。** 会话、模型请求和文件缺少完整的自动到期和空间回收机制。

## 建议的 PoC 范围

若要继续验证，建议只使用非生产资源：

```text
3名内部测试用户
+ 3个个人Scope
+ 1个共享项目Scope
+ 1个只读知识源
+ 1个测试代码仓库
+ 1个低权限测试凭据
+ 1个定时项目汇报任务
```

必须测试：

- 个人文件、记忆和凭据不能被其他个人 Scope 读取；
- 共享频道只能看到所有参与者共同有权看到的历史；
- 新增或移除成员后 Provider Session 被正确重置；
- once Grant 使用后失效，standing Grant 可撤销；
- 命令审批、拒绝、超时和任务重试不会重复产生副作用；
- 沙箱出网与凭据日志可被审计；
- 管理员读取和数据保留符合内部政策。

## 采用分级

| 等级 | 建议 |
|---|---|
| 架构参考 | 立即保留 Scope、确定性权限、Harness Adapter、持久沙箱和 Worker Lease 思想 |
| 静态研究 | 已完成，持续跟踪上游安全边界和成熟度 |
| 受控 PoC | 真实多人场景出现后启动，使用测试账号和最低权限凭据 |
| 部门试点 | PoC 通过跨 Scope 泄漏、任务幂等和运维测试后再评估 |
| 敏感生产 | 专项安全评审、数据治理、kill switch 和平台适配完成前不进入 |

## 最终判断

QM 对我们最大的意义，是提供“从个人 Agent 到组织 Agent 平台”的参考骨架。当前应吸收架构而不是承诺生产采用；只有当多人协作、共享资源与权限隔离成为真实产品需求时，才值得支付云基础设施、平台适配和安全治理成本。
