一句话理解

大模型是大脑，工具是手脚，记忆是上下文，AgentScope 是把它们组织起来的运行骨架。

不是 Pi / Codex 这类可直接工作的成品 Agent。
01 / POSITION

它提供什么，
又不替你做什么？

判断一个 Agent 框架是否有用，关键不是功能名有多少，而是分清“框架能力”和“业务能力”的边界。

FRAMEWORK

可复用的 Agent 基础设施

减少重复搭建模型调用和工具循环的工作，把开发重点推向业务本身。

  • 01模型接入

    统一接入不同模型协议和消息格式。

  • 02工具系统

    把 Python 函数注册为模型可调用的工具。

  • 03Agent 循环

    组织思考、调用、回填结果和继续决策。

  • 04结构化输出

    用数据模型约束最终结果，便于系统消费。

  • 05多 Agent / 工作流

    支持消息传递、协作编排和人工介入。

  • 06观测与扩展

    保留调用过程，并可扩展存储和服务能力。

BOUNDARY

框架不会自动获得业务知识

AgentScope 给出接入入口和运行机制，实际工具、数据和规则仍由我们提供。

内容主要提供方我们的工作
语言理解与决策MiniMax M3选择模型、提示词与预算
循环、调度、格式AgentScope配置与二次开发
查事件、取证、计算我们编写的工具实现、鉴权、测试、审计
业务数据与事实我们的数据源治理来源、质量与权限
产品体验与安全我们的应用前后端、监控、审批、降级
MEMORY

有记忆接口，但要选择存储与策略

“支持记忆”不等于开箱就拥有永久、可靠、可治理的记忆。

本实验已用

进程内记忆

InMemoryMemory 保存本轮对话和工具结果；程序退出后消失。

框架可接

持久化记忆

可选 Redis、SQLAlchemy 或 Tablestore 等后端，负责跨进程保存。

需另行验证

长期记忆

可接 Mem0、ReMe 等组件，但召回、遗忘、隐私与成本仍需设计。

01 / 观测证据

工具直接返回

事件时间、位置、来源记录。可以追溯，但仍取决于上游数据质量。

02 / 确定性计算

程序计算得到

44.1 公里 / 11 分钟、149.6 公里 / 14 分钟。不是模型心算。

03 / 模型推断

需要显式降级

天气影响通信、典型强对流半径等说法未由工具提供，不能混入“证据”。

最重要的发现

MiniMax M3 能正确使用 AgentScope 的多轮工具调用，但会把合理的领域推断写成证据。下一版必须在数据结构上强制区分“观测、计算、推断”。

05 / DECISION

对我们的意义：
可以二次开发，但先做评测。

它能缩短 Agent 基础设施建设时间，是否最终采用，要看它是否明显优于“单次模型调用 + 固定业务代码”。

适合

作为上层 Agent 服务底座

  • 事件核验与结构化研判
  • 多工具调查和证据保留
  • 需要模型切换或多 Agent 编排
不替代

数据与产品基础设施

  • 不替代采集、清洗和数据库
  • 不替代业务工具与权限设计
  • 不自动保证事实正确或安全
下一目标

20 个固定案例对照评估

  • 工具选择、证据引用、反证保留
  • 重复一致性、延迟和费用
  • 工具错误时的安全降级
阶段目标

从“框架能跑通”推进到“真实任务上，质量、成本和可控性值得采用”。
