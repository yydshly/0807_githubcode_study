01 / VERDICT

一句话判断

信息源决定输入上限；Profile 与筛选决定信噪比；编辑和发布决定它能否成为日常工具。
相同点

与 AI 探测雷达同类

都是“来源配置 + 滑动时间窗口 + 批量抓取 + 去重筛选 + 结果输出”的信息处理系统。

差异点

强在编辑编排

Profile 路由、AI 评分、语义去重、类别配额、内容增强和双语日报形成了完整阶段链路。

现实边界

来源并不丰富

公开运行配置只有 14 个入口，且明显偏向 AI 推理框架、开源模型社区与技术新闻。

复用方向

借结构，不照搬源

适合吸收分阶段产物和编辑机制；来源治理、证据留存和事实核验仍需雷达自身建设。

03 / ACQUISITION

抓取方式是通用能力

RSS 不是信息源本身，而是一种统一发布协议。配置中的每个 Feed 地址才是具体来源；“RSS 全文提取”是在拿到 Feed 后，再访问文章页面补正文。

API

结构化接口

HN、GitHub、GDELT、OSS Insight。字段稳定，但仍受限流、配额和时间窗口影响。

RSS / Atom

统一订阅协议

低成本获取标题、链接、摘要和发布时间；内容完整度由发布者决定。

HTML

公开页面解析

Reddit、Telegram 等无 Key 路径。页面结构变化和反爬会影响长期稳定性。

FULL TEXT

正文二次提取

Feed 只给摘要时访问原文，用 Trafilatura 抽取正文；失败则回退 Feed 内容。

BROWSER

浏览器自动化

Twitter/X 可用 Cookie 和网络响应拦截，维护成本、账号风险最高。

AGGREGATOR

第三方聚合

Apify、OpenBB、RSS 桥接降低开发成本，同时引入费用、许可与服务依赖。

04 / PIPELINE

时间节点怎样判断

调度器生成统一的 since 截止时间，各抓取器按自己的能力过滤。判断通常基于条目发布时间，不是本次抓到的时间。

01生成窗口

例如运行时间减去 24 小时或 168 小时，形成统一 since。

02来源内获取

API 查询、Feed 批量下载或页面解析，各来源先执行数量与热度粗筛。

03解析发布时间

优先读取来源的 published_at；能解析时才与窗口截止点比较。

04统一与去重

转换为 ContentItem，保留 published_at 与 fetched_at，再做 URL 去重。

例外需要警惕

OSS Insight 是排名快照，实现把发布时间写成抓取时间；Google News 把窗口转换成查询语法；部分来源缺少可靠发布时间。因而“窗口内抓到”不总等于“事件发生在窗口内”。

配置来源→并发抓取→统一模型→URL 去重→Profile 路由→AI 评分→语义去重→日报发布
05 / COMPARISON

对 AI 探测雷达的意义

不是替换现有雷达，而是把它当作“编辑层参考实现”。真正的竞争力仍然来自你拥有、维护并理解的信息源网络。

NEXT
