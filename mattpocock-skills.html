01 / HOW IT WORKS

能力来自流程设计，
不是模型参数升级。

Skill 是可按需加载的工程操作说明。真正的可靠性来自四个相互配合的机制：正确路由、技能组合、项目记忆和外部反馈。

02 / DEVELOPMENT FLOW

从项目配置到长期维护，
八个阶段各自回答一个问题。

这是一张问题地图，不是固定瀑布。点击任一阶段查看输入、输出和对应技能；进入技能目录后可以继续筛选。

反馈不是最后一步。

验证阶段一旦发现“需求理解错误”或“领域术语冲突”，流程应回到澄清与建模；维护阶段出现新需求，也从重新对齐开始。

03 / ENGINEERING LINEAGE

Skill 是表现形式，

05 / ADOPTION PATH

先建立最小闭环，
再为复杂项目增加治理。

是否值得采用，取决于项目寿命、需求复杂度、测试反馈和跨会话协作成本，而不是技能数量越多越好。

01 / 快速探索

先避免做错方向

grill-with-docs→prototype→code-review

适合新想法、交互方向和一次性验证。保留轻量，不强行引入完整 Issue 流程。

02 / 持续开发

建立工程主闭环

setup→to-spec→to-tickets→implement / tdd→code-review

适合已有测试、需要持续迭代的真实产品。这是最值得优先试用的组合。

03 / 大型工作

增加决策与接力治理

wayfinder+research+triage+handoff

适合跨多次会话、多参与者和高决策密度项目，把“雾区”与进度显式留在外部系统。

06 / LIBRARY COMPARISON

Matt 是工程骨架，
David 是通用能力候选池。

两者都在增强 Agent 的工作方法，但调度方式、外部依赖和适用范围不同。最稳妥的组合不是双库全装，而是以工程主流程为骨架，再按真实缺口补充单项能力。

07 / BOUNDARIES

它增强的是工程纪律，
不是模型、工具或权限。

第三方 Skill 会直接影响 Agent 的行为。引入前应检查命令、写入目标、外部访问、提交策略和客户端能力，并根据团队流程修改。

阅读 Agent Skills 规范 ↗
它能做什么它不能替代什么
规定任务流程和完成标准不能提高模型参数能力
指导如何使用已有工具不能自动提供 MCP、账号或权限
把项目知识写入外部载体不能保证自然语言指令确定执行
改善反馈、审查和交接不能替代团队判断与安全审计
